## 1\. Задание

Разработать работающее Django-приложение для просмотра и фильтрации операций.

Приложение должно использовать **SQLite, SQL, Python `sqlite3`, маршрутизацию Django, URL-конвертеры, view-функции, шаблоны Django, GET-параметры, фильтры шаблонов и статические файлы**.

Результатом должна быть работающая система, в которой данные проходят следующую цепочку:

**SQLite → SQL → Python `sqlite3` → Django view → context → Django templates → HTML/CSS/JavaScript.**

Приложение должно содержать:

* главную страницу;  
* страницу стоек;  
* страницу списка операций;  
* страницу конкретного операции;  
* GET-фильтрацию операций;  
* сортировку и ограничение выборки;  
* статистические запросы;  
* отображение результатов SQL-запросов на веб\-страницах;  
* обработку основных ошибок.

Django ORM для работы с данными в рамках контрольной работы не используется.

## 2\. Предметная область и структура данных

Приложение работает с двумя связанными сущностями: «Стойка» и «Операция».

### 2.1. Сущность «Стойка»

| Поле | Назначение |
| :---- | :---- |
| `id` | Уникальный идентификатор стойки |
| `name` | Номер стойки, например «Стойка A4» |
| `capacity` | Количество юнитов (U) |
| `rack_kind` | Назначение стойки: серверная, сетевая, хранение |

### 2.2. Сущность «Операция»

| Поле | Назначение |
| :---- | :---- |
| `id` | Уникальный идентификатор операции |
| `title` | Название операции, например «Замена диска» |
| `slug` | Уникальная текстовая часть URL для обращения к операции |
| `op_type` | Тип работ: апгрейд, диагностика, ремонт |
| `start_date` | Дата и время начала |
| `duration` | Продолжительность работ в минутах |
| `nodes` | Количество затронутых узлов |
| `status` | Состояние операции: запланирована, выполняется, выполнена |
| `rack_id` | Идентификатор стойки, в которой выполняются работы |

Поле `rack_id` должно связывать операцию с соответствующей стойкой.

Создать не менее **4 стоек и 8 операций**.

Данные должны содержать различные типы операций, даты, количества узлов, статусы и стойки, чтобы результаты выборок, сортировки и фильтрации отличались друг от друга.

* подсчёта количества записей с помощью `COUNT`;

Для запросов с изменяемыми значениями использовать параметризованные запросы.

1. Выполнить его в SQLite и проверить результат.  
2. Использовать запрос в соответствующей функции приложения.  
3. Передать результат в шаблон.  
4. Открыть веб\-страницу и убедиться, что отображаемые данные соответствуют результату запроса.

## 9\. Фильтрация операций

Реализовать GET-фильтрацию по количеству узлов.

Например:

`/operations/?nodes=2`

Пользователь должен иметь возможность задать минимальное количество узлов.

Фильтр должен работать по следующей цепочке:

**GET-запрос → `request.GET` → view → параметризованный SQL-запрос → SQLite → результат → context → шаблон.**

Значение, полученное от пользователя, не должно непосредственно включаться в строку SQL.

Реализовать форму с методом `GET`, позволяющую задать минимальное количество узлов.

При отсутствии результатов вывести понятное сообщение.

Проверить фильтрацию как минимум для двух значений параметра, дающих разные результаты.

## 15\. Фильтры Django-шаблонов

Использовать не менее трёх различных фильтров Django. Каждый фильтр должен выполнять конкретную задачу.

* **`date`** — отображать дату операции в формате `15.10.2026`.

Из перечисленных фильтров необходимо использовать не менее трёх.

Применение фильтров должно быть функционально оправдано.

## 20\. Принцип оценивания

**Практический результат без подтверждения соответствующей реализацией в коде не засчитывается.**

**Наличие требуемой конструкции в коде без её фактического использования в работающем сценарии также не засчитывается.**

Например:

* наличие `slug` без использования URL-конвертера не подтверждает выполнение критерия 15;  
* наличие `{% extends %}` без использования общего шаблона для нескольких страниц не подтверждает выполнение критерия 20;  
* вывод фиксированного количества операций вместо получения количества из базы данных не подтверждает выполнение критерия 4;  
* GET-параметр, который изменяет результат только средствами Python без использования параметризованного SQL-запроса, не подтверждает выполнение критерия 12;  
* SQL-запросы в `queries.sql`, которые не используются работающим приложением, не подтверждают выполнение соответствующих критериев;  
* получение результата запроса в Python без передачи его в шаблон и отображения на веб\-странице не подтверждает выполнение требования об отображении результатов в Web;  
* отображение заранее заданных в HTML данных вместо результатов SQLite не подтверждает выполнение критериев получения и отображения актуальных данных;  
* наличие подключённого CSS-файла без фактического изменения оформления страницы не подтверждает выполнение критерия 25;  
* наличие файла JavaScript без его подключения и использования в интерфейсе не подтверждает выполнение критерия 26\.

## 21\. Порядок демонстрации

Работу демонстрировать в следующей последовательности:

**Запуск приложения → главная страница → навигация → страница стоек → список операций → связанные данные → GET-фильтрация → отсутствие результатов → сортировка и ограничение → страница операции по `slug` → 404 → обработка ошибки БД → общий шаблон → карточка операции → условное отображение → фильтры шаблонов → статистические SQL-запросы → отображение статистики в Web → изменение данных → CSS и логотип → интерактивный элемент JavaScript → полный пользовательский сценарий.**

При демонстрации работы с базой данных студент должен:

1. Выполнить SQL-запрос в SQLite и показать полученный результат.  
2. Открыть соответствующую страницу Django-приложения.  
3. Продемонстрировать, что на странице отображаются данные из результата запроса.  
4. Изменить запись в таблице `racks` или `operations`.  
5. Обновить страницу и показать актуальные данные.  
6. Добавить несколько операций и проверить изменение статистики, включая результат запроса с `HAVING`.

Изменение данных выполняется непосредственно в SQLite. После изменения необходимо повторно обратиться к странице приложения и проверить, что она отображает актуальные данные базы.
